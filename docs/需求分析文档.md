## 1. 引言

### 1.1 编写目的

本文档旨在对"基于AI智能的电商商品销售分析与预测系统"进行全面的需求分析，明确系统的功能需求、非功能需求、数据需求和运行约束。文档的预期读者包括：

| 读者 | 用途 |
|------|------|

### 1.2 项目背景

随着电商行业竞争加剧，传统报表式数据分析已无法满足精细化运营需求。企业需要借助机器学习和数据挖掘技术，从海量交易数据中提取销售趋势、用户行为模式和库存风险信号，实现由"经验驱动"向"数据驱动"的决策转型。

本项目面向电商平台的实际运营场景，构建一个集**多维数据分析、销售预测、用户画像、智能预警**于一体的商业智能系统，帮助运营团队提升库存周转率、优化营销策略和提高销售转化率。

| **分析考核与选题要求** | 对照《软件工程》课程实践考核要求说明和选题说明，确保覆盖所有要求的功能点 | 需求覆盖度检查清单 |

需求的筛选遵循以下原则：
- **必要性**：每一项需求必须能追溯到选题说明中的功能要求或实际业务场景
- **可行性**：在课程项目剩余时间（约10–14天）和技术约束（Python + scikit-learn + Vue 3 + MySQL）内可实现
- **价值性**：优先保留对"数据驱动决策"有直接贡献的需求，剔除纯技术炫技类需求

> 被筛除的需求示例：实时流式数据处理（需 Kafka/Flink，超出技术栈范围）、深度学习预测模型（LSTM/Transformer，与"不要过于深奥"的约束相悖）

## 2. 任务概述

### 2.1 系统目标

本系统的核心目标是构建一个**基于机器学习和大数据分析的电商销售智能决策平台**，具体包括：

1. **分析能力**：支持按时间、地域、品类等多维度对销售数据进行下钻和聚合分析
2. **预测能力**：基于历史销售数据，利用时序预测算法输出未来销售趋势和库存需求
3. **洞察能力**：构建用户画像，识别高价值客户群体，驱动个性化推荐
4. **预警能力**：自动检测销售额异常波动、库存风险等并触发告警
5. **可视化能力**：以交互式图表和仪表盘形式呈现分析结果，支持报表导出

### 2.2 用户角色分析

系统识别出以下四类参与者（Actor）：

| 角色 | 职责概述 | 典型场景 |
|------|----------|----------|
| **电商运营经理** | 日常销售监控、营销决策、库存管理 | 查看今日销售概况、核查异常预警、制定促销策略 |
| **数据分析师** | 深度数据分析、预测模型配置、报表定制 | 按品类/地区下钻分析、调整预测参数、制作周报 |
| **高层管理者** | 全局经营状况概览、战略决策支持 | 查看月度经营仪表盘、对比季度业绩趋势 |
| **系统管理员** | 系统配置、用户权限管理、数据源维护 | 创建用户账号、配置数据接入、管理预警规则 |

### 2.3 运行环境概览

系统采用 **B/S 架构**（浏览器/服务器），用户通过 Web 浏览器访问，主要部署环境如下：

- **客户端**：Chrome（≥90）、Firefox（≥88）、Edge（≥90）、Safari（≥14）
- **服务端**：Linux/Windows Server，Python 3.10+，MySQL 8.0+
- **网络**：支持内网部署，若需远程访问则通过 HTTPS 加密通道

### 2.4 可行性分析

#### 2.4.1 技术可行性

| 维度 | 评估 |
|------|------|
| **数据获取** | Kaggle 等平台提供公开电商数据集（如 Retail Rocket、E-Commerce Data），数据体量和字段丰富度满足项目需求 |
| **预测模型** | Python scikit-learn 提供成熟的时序预测算法（LinearRegression、ARIMA 的 statsmodels 实现），无需深度学习框架；课程项目级别精度要求（MAPE ≤ 20%）可达到 |
| **Web 开发** | Vue 3 + Element Plus 提供开箱即用的仪表盘组件（图表、表格、筛选器）；Python Flask/FastAPI 提供轻量级 RESTful API，组员有课程项目经验 |
| **数据库** | MySQL 8.4 满足关系型数据存储需求，10 张核心表的规模在单机部署下性能无瓶颈 |

#### 2.4.2 进度可行性

| 维度 | 评估 |
|------|------|
| **团队规模** | 5 人，实际可用约 10–14 天，分工为：前端核心页面1人、前端管理页面+测试1人、后端核心1人、后端数据1人、ML算法1人 |
| **工作量评估** | 10 个用例中 P0（5个）必须完成，P1（3个）力争完成，P2（2个）时间不足时仅提供伪代码和设计；关键代码行数目标 ≥ 800 行（超过 500 行底线） |
| **缓冲时间** | 第12天起停止新功能开发，集中精力测试打磨和演示准备 |

#### 2.4.3 社会可行性

| 维度 | 评估 |
|------|------|
| **数据合规** | 使用 Kaggle 公开数据集（非真实用户数据），不涉及个人信息保护法合规问题；若演示阶段导入真实竞品数据，需确保数据来源合法（不使用爬虫采集竞品网站） |
| **伦理考量** | 用户画像功能仅用于商业分析场景的群体特征统计，不涉及个人敏感信息推断或歧视性标签 |

### 2.5 假设与依赖

| 类别 | 假设/依赖 | 风险 | 缓解措施 |
|------|----------|------|----------|
| **数据假设** | Kaggle 电商数据集至少包含12个月销售记录，字段覆盖商品、用户、订单、时间、地域等维度 | 数据字段不完整 | 方案B：Python脚本模拟补充缺失字段 |
| **数据假设** | 销售数据已做脱敏处理，不包含真实消费者个人信息 | — | 使用前检查数据字段，移除姓名/手机号等列 |

| **团队假设** | 5名组员均能投入每周8-10小时的项目时间 | 个别成员投入不足 | 组长每日检查进度，发现卡点立即协调 |

#### UC-01：多维度销售数据查询与分析

| 项目 | 内容 |
|------|------|
| **用例编号** | UC-01 |
| **用例名称** | 多维度销售数据查询与分析 |
| **参与者** | 电商运营经理、数据分析师、高层管理者 |
| **优先级** | 高（P0） |
| **前置条件** | 用户已登录且具有数据查看权限；系统中已有至少一个完整销售周期的数据 |
| **触发条件** | 用户进入数据分析页面，选择查询维度 |

**基本流程**：

1. 用户进入"销售数据分析"模块
2. 系统展示默认视图：最近 7 天的全品类销售概况（总销售额、总订单量、环比变化率）
3. 用户选择分析维度，维度可自由组合：
   - **时间维度**：按日 / 按周 / 按月 / 自定义区间
   - **地域维度**：全国 / 省 / 市
   - **品类维度**：一级类目 / 二级类目 / 具体 SKU
   - **渠道维度**：PC 端 / 移动端 / 小程序
4. 用户点击"查询"，系统在 2 秒内返回结果
5. 系统以**数据表格 + 可视化图表**（趋势折线图、构成饼图、对比柱状图）并排展示分析结果
6. 用户可对结果进行排序、筛选、切换图表类型

**异常流程**：

| 异常场景 | 处理方式 |
|----------|----------|
| 所选维度无数据 | 提示"当前筛选条件下暂无数据，请调整维度" |
| 查询超时（>5秒） | 提示"数据量过大，建议缩小查询范围或导出后查看" |
| 数据源连接失败 | 提示"数据加载失败，请稍后重试"，记录错误日志 |

**后置条件**：查询结果展示在页面上，用户可选择导出或进一步下钻

#### UC-02：销售趋势预测

| 项目 | 内容 |
|------|------|
| **用例编号** | UC-02 |
| **用例名称** | 销售趋势预测 |
| **参与者** | 电商运营经理、数据分析师 |
| **优先级** | 高（P0） |
| **前置条件** | 系统中至少有 12 个月的历史销售数据 |
| **触发条件** | 用户进入"销售预测"模块 |

**基本流程**：

1. 用户进入"销售预测"页面
2. 系统默认展示：基于过去 12 个月数据的未来 30 天全品类销售额预测曲线
3. 用户可配置预测参数：
   - **预测范围**：全品类 / 指定品类 / 指定 SKU
   - **预测周期**：未来 7 天 / 30 天 / 90 天
   - **预测模型**：默认自动选择（也可手动选：移动平均 / 线性回归 / ARIMA）
4. 用户点击"开始预测"，系统调用预测模型进行计算
5. 系统展示：
   - 预测曲线图（历史实际值 + 预测值，含置信区间阴影）
   - 预测结果的 MAPE 值和可信度评估
   - 关键转折点标注（如"预计 6 月 15 日达到销售峰值"）

**异常流程**：

| 异常场景 | 处理方式 |
|----------|----------|
| 历史数据不足 12 个月 | 提示"历史数据不足，预测结果仅供参考"，降低置信区间显示 |
| 预测模型计算超时（>10秒） | 提示"预测计算时间较长，系统将在后台完成计算后通知您" |
| 所选品类数据波动过大 | 标注"该品类销售波动较大，预测准确度可能较低" |

**后置条件**：预测结果展示在页面上，用户可导出预测报告

#### UC-03：库存需求预测

| 项目 | 内容 |
|------|------|
| **用例编号** | UC-03 |
| **用例名称** | 库存需求预测 |
| **参与者** | 电商运营经理 |
| **优先级** | 高（P0） |
| **前置条件** | 系统有对应 SKU 的历史销售数据和当前库存数据 |
| **触发条件** | 用户进入"库存预测"模块 |

**基本流程**：

1. 用户进入"库存需求预测"页面
2. 系统展示：库存健康状况总览（安全库存、预警库存、缺货风险三类标记）
3. 用户选择预测范围：全部 / 指定品类 / 指定 SKU
4. 系统根据历史销量 + 季节因子 + 销售趋势，计算未来 30 天的库存需求
5. 系统展示预测结果：
   - 当前库存 vs 预测需求量对比
   - 库存周转天数
   - 建议补货量及补货时间窗口

**异常流程**：

| 异常场景 | 处理方式 |
|----------|----------|
| SKU 无历史销售数据（新品） | 提示"该商品无历史数据，请手动设置初始预测参数" |
| 当前库存数据缺失 | 提示"库存数据未同步，请联系管理员检查数据源" |

#### UC-04：用户画像查看

| 项目 | 内容 |
|------|------|
| **用例编号** | UC-04 |
| **用例名称** | 用户画像查看 |
| **参与者** | 电商运营经理、数据分析师 |
| **优先级** | 中（P1） |
| **前置条件** | 系统已采集足够的用户行为数据 |
| **触发条件** | 用户进入"用户画像"模块 |

**基本流程**：

1. 用户进入"用户画像"模块
2. 系统展示客户群体总览：用户价值分层（高/中/低价值）、新老客占比、活跃度分布
3. 用户选择某一客群或具体用户
4. 系统展示画像标签：
   - **基础属性**：性别、年龄段、地域
   - **消费特征**：客单价、购买频次、偏好品类、促销敏感度
   - **行为特征**：浏览时长、加购率、复购率、退货率
5. 用户可基于画像标签筛选目标人群并导出人群包

**异常流程**：

| 异常场景 | 处理方式 |
|----------|----------|
| 用户行为数据总量不足（如新系统上线不满1个月） | 提示"数据积累不足，画像标签将在数据充足后自动更新"，暂不展示画像，仅展示基础统计 |
| 某画像维度数据缺失（如用户未填写性别） | 该维度标注"未知"，不影响其他维度的计算和展示 |
| 数据采集管道异常导致近期行为数据缺失 | 标注"最近 X 天数据未更新"，使用历史画像快照作为临时展示 |
| 所选客群规模过小（如 < 50 人） | 提示"客群规模过小，统计意义有限，建议扩大筛选范围" |

#### UC-08：异常销售检测与预警

| 项目 | 内容 |
|------|------|
| **用例编号** | UC-08 |
| **用例名称** | 异常销售检测与预警 |
| **参与者** | 电商运营经理、数据分析师 |
| **优先级** | 高（P0） |
| **前置条件** | 系统已配置预警规则 |
| **触发条件** | 系统定时巡检（每 1 小时）或用户手动触发 |

**基本流程**：

1. 系统定时扫描最新销售数据，与历史基线对比
2. 检测到异常时，系统通过以下渠道发出告警：
   - **系统内告警**：在系统首页预警栏高亮显示（红色=严重、橙色=警告、黄色=提示）
   - **邮件通知**（可选）：向配置了邮件通知的用户发送告警邮件
   - 异常类型示例：销售额突降 30%+、某 SKU 库存触及警戒线、退货率异常飙升
3. 用户点击预警条目，查看详细分析：
   - 异常数据与正常基线的对比
   - 可能原因推测（如"正值大促后回落期"、"该商品出现集中差评"）
   - 建议处置措施（如"建议暂停该商品广告投放，核查差评原因"）
4. 用户可将预警标记为"已处理"或"忽略"，标记后该预警从首页消除

**异常流程**：

| 异常场景 | 处理方式 |
|----------|----------|
| 预警规则配置错误（如阈值设置为0） | 系统校验规则参数，不合法的规则自动禁用并通知管理员 |
| 同一异常重复触发（如连续3次扫描均检测到同一问题） | 不重复生成预警条目，在原条目上更新"持续时长" |
| 预警扫描任务执行超时 | 记录错误日志，下次扫描时自动重试，连续3次失败后通知管理员 |

### 4.2 安全性需求

| 需求项 | 描述 |
|--------|------|
| 身份认证 | 用户名 + 密码登录，密码以 bcrypt 哈希存储，不可逆 |

| 权限控制 | 基于角色的访问控制（RBAC），不同角色可访问的菜单和功能不同 |

| 敏感数据保护 | 用户密码、手机号等个人信息加密存储或脱敏展示 |

### 4.3 可靠性需求

| 需求项 | 描述 |
|--------|------|
| 可用性 | 系统应保证 7×24 小时正常运行（演示期间可放宽） |
| 故障恢复 | 非硬件故障导致的系统宕机，应在 5 分钟内恢复 |
| 数据备份 | 数据库每日自动备份，保留最近 7 天的备份文件 |
| 异常处理 | 所有未捕获异常统一记录日志，前端展示用户友好的错误提示 |

### 4.4 可维护性需求

| 模块化 | 前端组件、后端 API、ML 模型分层独立，模块间低耦合 |
| 日志 | 关键操作（登录、预测、导出、管理操作）记录日志，含时间戳和执行结果 |

### 6.3 数据采集说明

由于本项目为课程实践，电商数据不来自真实生产环境。数据来源有两种可选方案：

| 方案 | 来源 | 优点 | 缺点 |
|------|------|------|------|
| 方案A | 公开数据集（Kaggle 电商销售数据集、阿里天池数据集） | 数据真实、体量够 | 字段需映射适配 |
| 方案B | Python 脚本生成模拟数据 | 可控性强、字段完全匹配 | 数据可信度打折扣 |

**建议采用方案 A 为主 + 方案 B 补充**，使用 Kaggle 电商数据集作为核心销售数据，对于预测和预警场景用脚本补充标注数据。
