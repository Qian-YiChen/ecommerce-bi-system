【协作模式 — 与AI配合的经验总结】（来自 project-brief.txt）
  1. 需求分析文档 vs 知识库对比审核：
     - 先把知识库PDF用 pdftotext -layout -enc UTF-8 提取为文本，再对照审核
     - 审核重点：缺失章节、建模不完整、知识库概念未显式应用
  2. 文档修改流程：
     - 先出审核报告，逐项确认后再修改
     - 修改时跳过图表类问题（后续自行用Draw.io补UML图）
     - 改完要交叉验证两份文档之间的一致性（如需求文档 vs 分工文档的时间/优先级）
  3. 代码产出：
     - 后端统一放 backend/，前端放 frontend/，ML放 ml/，文档放 docs/
     - 严辰乐的代码如果依赖别人的函数，不要留空等——写「函数参数需求文档」约定签名
     - 认证模块当前 import 会报错是正常的，等苏文韬交付 db_service.py 即解
  4. GitHub：
     - 只上传工程/文件夹，不上传整个软工大作业
     - HTTPS push 需要 Personal Access Token（密码已不可用）
     - Token 有效期90天，过期后需重新生成
  5. PDF 提取：
     - 知识库PDF中文内容用 pdftotext -layout -enc UTF-8 可正确提取
     - 不要用 Python PyPDF2（中文乱码），不要用 Read 工具（需要 pdftoppm）
  6. 环境问题：
     - WindowsApps 下的 python3 会超时/权限受限，必须用 D:\Anaconda\python.exe
  7. Git 踩坑：
     - 首次 push 用完整 Token URL 会导致后续 `git push` 报 "no upstream branch"
     - 解决：`git push --set-upstream origin main` 绑定一次即可
     - 覆盖同步用 `git commit --allow-empty -m "..."` + `git push`
  8. 文档产出节奏：
     - 需求分析文档、软件设计文档、项目管理文档、团队分工说明 — 四份核心文档
     - 前两份重点在"完整"，后两份重点在"可执行"
     - 不依赖组员的章节先写完，依赖组员的标注 ⏳ 后续补
  9. 组员接口约定：
     - 「函数参数需求文档.md」是关键产物 — 严辰乐的代码通过它解耦组员依赖
     - 每个函数约定清楚：签名、参数类型、返回 JSON 结构、注意事项
