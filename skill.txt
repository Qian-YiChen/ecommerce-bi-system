【协作模式 — 与AI配合的经验总结】（来自 project-brief.txt）
  1. 需求分析文档 vs 知识库对比审核：
     - 先把知识库PDF用 pdftotext -layout -enc UTF-8 提取为文本，再对照审核
     - 审核重点：缺失章节、建模不完整、知识库概念未显式应用
  2. 文档修改流程：
     - 先出审核报告，逐项确认后再修改
     - 修改时跳过图表类问题（后续自行用Draw.io补UML图）
     - 改完要交叉验证两份文档之间的一致性（如需求文档 vs 分工文档的时间/优先级）
  3. 代码产出：
     - 后端统一放 backend/，前端放 frontend/，ML放 ml/，文档放 docs/
     - 严辰乐的代码如果依赖别人的函数，不要留空等——写「函数参数需求文档」约定签名
     - 认证模块当前 import 会报错是正常的，等苏文韬交付 db_service.py 即解
  4. GitHub：
     - 只上传工程/文件夹，不上传整个软工大作业
     - HTTPS push 需要 Personal Access Token（密码已不可用）
     - Token 有效期90天，过期后需重新生成
  5. PDF 提取：
     - 知识库PDF中文内容用 pdftotext -layout -enc UTF-8 可正确提取
     - 不要用 Python PyPDF2（中文乱码），不要用 Read 工具（需要 pdftoppm）
  6. 环境问题：
     - WindowsApps 下的 python3 会超时/权限受限，必须用 D:\Anaconda\python.exe
  7. Git 踩坑：
     - 首次 push 用完整 Token URL 会导致后续 `git push` 报 "no upstream branch"
     - 解决：`git push --set-upstream origin main` 绑定一次即可
     - 覆盖同步用 `git commit --allow-empty -m "..."` + `git push`
     - 未 push 成功的本地 commit 可用 `git commit --amend --no-edit` 修复后重推
     - amend 后 commit hash 会变，这是正常的
  8. GitHub Token 安全：
     - Token 绝不能写入会被 push 到 GitHub 的文件中
     - GitHub Push Protection 会扫描提交内容，检测到 Token 明文会拒绝 push
     - Token 一旦在对话/文件中暴露，立即去 GitHub Settings → Developer settings → Tokens 删除并重新生成
     - 正确做法：Token 放在工程目录外的独立文件（如 ../githubToken.txt），代码中用相对路径引用
     - git remote 中的 Token：`git remote set-url origin https://<新token>@github.com/...`
  9. Git 代理配置：
     - 查看 Windows 系统代理：reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" | grep ProxyServer
     - 常见代理端口：Clash 7890/7897，V2Ray 10809
     - 配置：git config --global http.proxy http://127.0.0.1:端口
     - 同时设置 https.proxy 保持一致
  10. 文档产出节奏：
     - 需求分析文档、软件设计文档、项目管理文档、团队分工说明 — 四份核心文档
     - 前两份重点在"完整"，后两份重点在"可执行"
     - 不依赖组员的章节先写完，依赖组员的标注 ⏳ 后续补
  11. 组员接口约定：
     - 「函数参数需求文档.md」是关键产物 — 严辰乐的代码通过它解耦组员依赖
     - 每个函数约定清楚：签名、参数类型、返回 JSON 结构、注意事项

  12. 文件处理 — sed 中文问题：
     - sed 处理含中文全角字符（如 ()「」）的替换容易报 "unterminated s command"
     - 替代方案：用 Python 做 UTF-8 文件替换
       D:\Anaconda\python.exe -c "...c=c.replace('旧','新')..."

  13. MySQL 安装与初始化（2026-06-08 实战）：
     - winget install Oracle.MySQL 只安装程序文件，不自动初始化
     - 安装后需手动：
       a. 创建数据目录（不能在 Program Files 下，权限不够）
       b. mysqld --datadir="用户目录/mysql-data" --initialize-insecure（生成 root 无密码）
       c. mysqld --defaults-file="my.ini" &（后台启动）
       d. mysql -u root → ALTER USER 'root'@'localhost' IDENTIFIED BY '123456'（设密码）
     - MySQL 8.4 不支持 default_authentication_plugin=mysql_native_password 参数
     - 数据物理位置：C:\Users\MSI-NB\mysql-data\ecommerce_bi\*.ibd
     - 每个数据库 = 一个子目录，每张 InnoDB 表 = 一个 .ibd 文件
     - mysqld（带 d = daemon/服务器进程）不等于 mysql（客户端），先启动服务器才能连接

  14. 数据库坑 — mape 列类型：
     - DECIMAL(5,4) 最大只能存 9.9999，MAPE 百分比可达 100%+ → 写入报错
     - 修复：ALTER TABLE ... MODIFY mape DECIMAL(8,2)
     - 建表时要根据实际数值范围选择 DECIMAL 精度

  15. ML 模块集成经验：
     - pd.read_sql() 直接传 pymysql.Connection 会出 UserWarning，但能正常工作
     - 线性回归做基线模型时 MAPE 可能 100%+，对小数据集属于正常
     - 递归预测时无法更新 lag_7/lag_30，只能用 lag_1 + rolling_mean
     - 库存数据必须来自数据库真实值，不能用 MOCK_INVENTORY 随机生成
     - ML 模块需提供独立 API 函数（load_model、predict_xxx_for_api），
       不能只靠 main() 一次性跑全流程

  16. 文档审计经验：
     - 函数参数需求文档的函数签名必须和实际交付代码严格一致
     - 设计文档中模块名应与实际文件结构对应
       （如 docs 写 sales_predict/stock_predict 但代码是单一 ml_pipeline.py）
     - 表数量变更（9→10）需同步更新所有文档
     - 每次组员交付后应交叉比对：docs vs 实际代码 vs 项目结构总览

  18. Git 提交规范 — 每个文件独立 commit：
     - 不要用 git add . 一次性全部暂存
     - 每个逻辑独立的文件单独 commit，写清楚这个文件改了什么
     - 这样 git log 清晰可追溯，出问题知道从哪个 commit 回退
     - 示例：
       git add docs/函数参数需求文档.md
       git commit -m "文档：重写§3薛淞函数签名以匹配实际ml_pipeline.py交付"
       git add ml/ml_pipeline.py
       git commit -m "修复：MOCK_INVENTORY→数据库真实库存、新增category_id特征、新增4个API函数"

  17. Windows 编码坑：
     - Windows 终端默认 GBK，print emoji 会 UnicodeEncodeError
     - 解决：用英文标记，或 sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8')
     - curl 输出中的中文 JSON 显示为 \uXXXX 是正常的（实际内容正确）
