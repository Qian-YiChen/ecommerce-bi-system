# 软件工程课程实践心得

**姓名**：严辰乐
**学号**：24325289
**角色**：组长 / 后端核心 / 项目管理
**日期**：2026-06-21

---

作为组长，我在本次实践中同时承担项目管理与后端核心开发两份责任，对软件工程的协作本质有了最深切的体会。

技术层面，我负责 Flask 框架搭建、JWT 认证模块、预测与预警 API、APScheduler 定时调度，以及 8 条 P1 路由的全量开发。最棘手的阶段出现在前后端对接。前端共 8 个页面、调用 24 条后端路由，初次联调时发现有 6 处 API 路径、请求方法或响应格式与后端不一致——有些是路径拼写错误，有些是 GET/POST 方法用反，有些是响应字段名不匹配。我把所有路由逐条对照 API 文档重新审查，发现根本原因在于文档更新滞后于代码变动。前端同学按旧版接口文档开发，后端在迭代中修改了路径结构但未同步通知。这个教训让我认识到：接口文档必须作为团队的"唯一真相源"，任何变更需第一时间更新文档并广播全员。

JWT 认证对接也踩了坑。前端登录后 token 的存储位置和请求头注入逻辑与后端的 `@jwt_required` 中间件预期不一致，导致登录成功但后续请求全部 401。排查后发现前端把 token 存到了 `sessionStorage` 但拦截器从 `localStorage` 读取，这类看似微小的细节恰恰是联调中最耗费时间的bug。

管理层面，最大的挑战是保持五份交付物的一致性。组员交付后，函数签名、数据库表数量、模块名称、API 路径等信息分散在需求文档、设计文档、接口约定文档、README 和项目结构总览中。每次任一变更，都需要交叉审计所有文档是否同步更新。曾因表数量从 9 张增至 10 张后设计文档未更新而被我在审查中发现。最终我建立起"交付即审计"的规则——任何组件交付后必须对照 4 份核心文档做一致性检查。

这次实践让我明白，组长的价值不仅是多写代码，更在于建立流程、拦截错误、确保五人团队产出的不是五个孤立部件，而是一个真正集成的系统。
